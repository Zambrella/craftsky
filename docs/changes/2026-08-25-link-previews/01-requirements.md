# Requirements: Link Previews (Website Card Embeds)

## 1. Initial Request

Support website-card link previews in CraftSky, following the Bluesky model: URLs shared in a post can render as a card with title, description, and optional thumbnail, and the selected card is frozen into the public post record. Determine whether the Flutter client or AppView fetches website metadata, then define composer, API, security, persistence, scheduled-post, and read/render behavior.

## 2. Current Codebase Findings

- Relevant files:
  - `lexicon/social/craftsky/feed/post.json` defines `embed` as an open union containing only the local `#quoteEmbed`; top-level post images are separate and currently may coexist with quote embeds.
  - `appview/internal/lexicon/craftsky/feedpost.go` is generated by `just lexgen`; the generator already maps `app.bsky.*` references to indigo's generated package.
  - `app/lib/feed/data/post_api_client.dart` creates posts through `POST /v1/posts`; `embed` currently carries only `{quote: ...}`. Image blobs upload through `POST /v1/blobs/images`.
  - `app/lib/feed/composer/composer_media_uploader.dart` keeps image bytes local and uploads at submission time.
  - `app/lib/shared/rich_text/facet_token_parser.dart` already detects ordered `LinkFacetToken`s, adds `https://` to bare domains, and trims supported sentence punctuation.
  - `app/lib/feed/models/post.dart` models images and hydrated quote previews but no external card.
  - `appview/internal/routes/policy.go` centralizes auth, device, body, and rate-limit policy. Existing limits are Write 60/minute and Upload 100/hour per token; neither is appropriate for outbound link fetching.
  - `craftsky_posts.record JSONB` already stores the complete authoritative public post record. All post-shaped read surfaces share `postSelectColumns` and `BuildPostResponse`/`BuildQuoteView`.
  - Standard and project composers support local drafts and scheduled posts. Scheduled thumbnail bytes are owner-private in the existing object store and are uploaded to the PDS by the existing publication worker.
- Existing patterns:
  - Flutter never talks to a PDS directly. AppView mediates writes and blob uploads using server-held PDS OAuth tokens.
  - AppView returns hydrated post views with display-ready media URLs; Flutter does not fetch PDS records in the happy path.
  - Composer media bytes are uploaded only when publishing or staged privately when scheduling.
  - Scheduled publication freezes its record before the PDS write and retries failed publication through the existing worker.
- Current behavior:
  - URLs become tappable link facets and open externally through `url_launcher`; no preview is fetched or rendered.
  - Quote posts occupy the single `embed` union slot.
- Constraints discovered:
  - Flutter web is a real target, so browser CORS prevents reliable client-side fetching of arbitrary pages.
  - Lexicon changes require the `atproto-lexicon` skill, an ADR, `just lexgen`, and committed generated output.
  - The current Bluesky `app.bsky.embed.external` type requires `uri`, `title`, and `description`, has an optional `image/*` blob capped at exactly 1,000,000 bytes, and has no title/description or thumbnail-dimension fields.
  - Existing CraftSky image upload and rendering paths support JPEG, PNG, and WebP.
  - No production deployment or trusted egress-proxy contract exists in the repository.
- Test/build commands discovered: `just lexgen`, `just test`, and `flutter test` from `app/`.

## 3. Clarifying Questions And Decisions

### Q1: Who fetches website metadata?
Answer: **AppView**.
Decision / implication: Flutter sends one normalized fragmentless transport URL to an authenticated AppView endpoint. AppView owns bounded HTTP fetching, parsing, redirects, SSRF defense, and thumbnail download. The selected result is still frozen into the PDS record at creation time.

### Q2: When is a URL eligible for previewing?
Answer: A URL must be followed by an explicit token boundary recognized by the shared facet syntax, such as whitespace or supported closing/sentence punctuation. End-of-draft alone is not a completion boundary.
Decision / implication: Fetch immediately when the explicit boundary appears; do not debounce. Derive candidates from `LinkFacetToken`s rather than maintaining a second URL regex.

### Q3: How do multiple URLs work?
Answer: Preview the first four distinct completed URLs in text order, one request at a time. Show successful previews as a left/right carousel; the selected card is the only card embedded.
Decision / implication: Default to the first successful URL in text order. Failed candidates are omitted without an error. Selection follows normalized URL identity across text reordering and falls back to the earliest remaining success if the selected URL is removed.

### Q4: How are duplicate URLs identified?
Answer: Add `https://` when absent, lowercase scheme/host, remove default ports and fragments for candidate identity and preview requests, and preserve path/query. Different fragments share fetched metadata. AppView returns the validated final redirect URL with only a redirect-supplied fragment. In Flutter, the first current text occurrence for a normalized identity supplies the source fragment, including its absence, only when the redirect returned no fragment; reordering or removing duplicates updates that client-composed destination without refetching metadata.
Decision / implication: Cache success and failure results in memory for the composer session. Removing and re-adding an equivalent URL does not refetch it. Selection remains attached to normalized identity while its source fragment follows the deterministic first-occurrence rule.

### Q5: How does dismissal work?
Answer: Dismissal opts the entire composer session out of link previews, cancels pending work, and prevents new fetches. A short `Link previews hidden` snackbar offers Undo.
Decision / implication: Dismissal is not persisted into local drafts. If Undo expires, reopening the composer as a new session is the way previews naturally become eligible again.

### Q6: What happens if the user submits while previews are loading?
Answer: Publish immediately without an external embed and ignore late results.
Decision / implication: Fetch latency never delays submission. A URL remains a normal link facet.

### Q7: Can images and an external card coexist?
Answer: **No. Images win automatically.** This exclusion applies only to external cards; images may still accompany quote embeds.
Decision / implication: Adding any post image hides previews and cancels pending fetches. Removing all images restores cached candidates and resumes queued work unless previews were dismissed. `POST /v1/posts` rejects images plus external. Federated records containing both remain indexed, but CraftSky read views omit the external card.

### Q8: Which lexicon type represents the card?
Answer: Reuse `app.bsky.embed.external` rather than defining a CraftSky-specific object.
Decision / implication: Add the standard type to the post's open union. CraftSky applies stricter API policy for metadata length and accepted thumbnail formats without freezing those restrictions into a redundant PDS schema.

### Q9: What are the API and rate-limit shapes?
Answer: `POST /v1/link-previews` accepts one `{url}` per request. Add a dedicated `link_preview` rate class at 60/hour per token and 120/hour per device.
Decision / implication: Singular requests isolate errors and cancellation. Flutter queues up to four candidates with one active request.

### Q10: How do scheduled posts and drafts behave?
Answer: Scheduled posts preserve the selected frozen card and privately stage its thumbnail. Local drafts do not persist preview state and refetch on reopen.
Decision / implication: Scheduled payloads gain optional standard external metadata plus an optional private thumbnail-media reference. Reopening a schedule reuses the frozen selected card while its source URL remains, and fetches only other/new candidates. Publication does not refresh metadata.

### Q11: Can a selected thumbnail fail publication?
Answer: Yes. Once the user has selected/kept a card with a thumbnail, immediate thumbnail-upload failure fails post submission, and scheduled-thumbnail staging failure fails schedule save.
Decision / implication: Keep the composer and selected card intact, show the existing post/schedule failure feedback, and let the user retry or dismiss previews. Scheduled PDS upload failures use the existing retry/needs-attention lifecycle. A card that originally has no thumbnail publishes normally without one.

### Q12: What network boundary is required?
Answer: Resolve and pin public DNS answers in AppView, reject mixed public/non-public answers, allow only HTTP port 80 and HTTPS port 443, and require direct pinned egress.
Decision / implication: Do not honor a generic environment proxy for this path. If production requires a proxy, previews stay disabled until a separately reviewed proxy provides equivalent DNS/IP/redirect enforcement. Production enablement is explicit through `LINK_PREVIEWS_ENABLED=true`.

### Q13: How is metadata parsed?
Answer: Use `golang.org/x/net/html.Tokenizer` directly after the controlled fetch, not `github.com/otiai10/opengraph/v2`.
Decision / implication: Parse only the bounded head stream, support Twitter fallbacks and legacy charsets, honor the first valid `<base href>` for relative image assets, and keep fetch/security behavior separate from extraction.

### Q14: How is public data stored and observed?
Answer: Read external data from the authoritative `craftsky_posts.record JSONB`; do not add a redundant public-post column. Emit no client product analytics and no host/URL/content in server telemetry.
Decision / implication: No public-post migration is required. Operational telemetry uses only bounded stage, result, error class, status class, redirect-count/byte buckets, and duration.

## 4. Candidate Approaches

### Option A: Client-side fetch
Summary: Flutter fetches and parses arbitrary pages and uploads the selected image.
Pros:
- No AppView egress surface.
- Superficially resembles Bluesky's client implementation.
Cons:
- Browser CORS breaks the web target.
- Every platform duplicates parsing, timeout, redirect, and MIME logic.
- Target sites receive repeated per-device traffic and abuse cannot be centrally bounded.
Risks: inconsistent cards and platform-specific failures.

### Option B: AppView fetch with standard record embed (selected)
Summary: AppView securely fetches one URL per request; Flutter manages a bounded candidate carousel and embeds one standard `app.bsky.embed.external` at publication.
Pros:
- Works consistently on web and native targets.
- Centralizes SSRF defense, limits, rate limiting, parsing, and observability.
- Keeps thumbnail bytes in the existing immediate/scheduled media flows.
- Produces an interoperable standard record embed without future refetching.
Cons:
- Adds an SSRF-bearing public-egress path.
- Requires changes across AppView, Flutter, lexicon generation, and scheduled publication.
Risks: DNS/redirect bypasses, slow targets, and broader regression scope.

### Option C: Hybrid metadata server plus client image fetch
Summary: AppView returns metadata/image URL and Flutter downloads the image.
Pros:
- Smaller metadata response.
Cons:
- Retains browser CORS and duplicated trust-boundary problems.
- Splits failure handling across server and client.
Risks: inconsistent previews and image-fetch failures on web.

## 5. Recommended Direction

Recommended approach: **Option B: AppView fetches; Flutter selects; the PDS record reuses `app.bsky.embed.external`.**

Why:
1. It preserves CraftSky's AppView-mediated network architecture and works on Flutter web.
2. It keeps the important Bluesky property: one frozen public card that readers never refetch.
3. Standard lexicon reuse improves interoperability and avoids a redundant load-bearing schema.
4. Explicit candidate, image-exclusion, scheduled-post, and failure rules make composer behavior deterministic.
5. Pinned public-only egress and dedicated limits contain the new abuse surface.

## 6. Problem / Opportunity

Pattern pages, shop links, tutorials, and inspiration links currently appear without context. Website cards make linked content legible in feeds while preserving chronological ranking and user-owned public records.

## 7. Goals

- G-001: Eligible URLs produce bounded, selectable composer previews without fetching while the user is still typing the token.
- G-002: An image-free post can freeze one selected standard external card into its PDS record.
- G-003: Immediate, scheduled, feed, detail, comment, profile, and quote-preview flows handle external cards consistently.
- G-004: All third-party network work is authenticated, rate-limited, time/size bounded, direct-egress pinned, and content-free in telemetry.

## 8. Non-Goals

- NG-001: No oEmbed, video player, PDF, JSON, image-document, favicon, or social-platform-specific embed support.
- NG-002: No client-side cross-origin metadata/image fetching.
- NG-003: No persistent or cross-user preview cache in v1.
- NG-004: No user editing of fetched title, description, or thumbnail.
- NG-005: No image resizing, transcoding, GIF/AVIF/SVG conversion, or oversized-thumbnail recovery.
- NG-006: No robots.txt processing, JavaScript execution, URL-shortener special cases, canonical-tag destination override, or metadata refresh at read/publication time.
- NG-007: No new product analytics, moderation policy, notifications, search behavior, or account-deletion behavior.
- NG-008: No generic egress-proxy support without equivalent separately reviewed SSRF guarantees.
- NG-009: No link-preview authoring or scheduled external cards in the project composer. Project posts continue to require at least one photo, which suppresses external previews under images-win; eligible federated image-free project records may still render external cards.

## 9. Users / Actors

| Actor | Description | Needs |
|---|---|---|
| Crafter | Composes or schedules an image-free post with URLs | Bounded previews, explicit selection, dismissal, and predictable failure behavior |
| Feed viewer | Reads posts and quote previews | A legible card with a safe, visible destination that opens externally |
| AppView operator | Runs the fetching and indexing service | Controlled rollout, bounded egress, safe telemetry, and no private-network access |

## 10. Current Behavior

- Link tokens become facets and open externally.
- `social.craftsky.feed.post#embed` accepts only the local quote variant.
- Public post records are retained in `craftsky_posts.record`, but read models expose no external card.
- Immediate and scheduled media flows handle only top-level post/profile media.

## 11. Desired Behavior

- **Composer:** the standard composer derives up to four distinct completed link candidates from shared facet tokens. Queue one preview fetch at a time. Show successful cards in text order with left/right controls and a position indicator. Images or quote composition suppress the feature. The project composer does not offer previews because its required photo always invokes images-win. Dismissal opts out for the session with a short Undo action.
- **Immediate submission:** if a successful selected card exists and no post images/quote exist, upload its thumbnail when present, then send `embed.external`. A pending/failed/absent/dismissed preview yields a normal post. A selected thumbnail upload failure fails submission and preserves the draft.
- **Scheduling:** privately stage the selected thumbnail, persist frozen standard external metadata in the scheduled payload, preserve it during edits, and publish it through the existing worker. Staging failure fails schedule save; later PDS failures follow existing retries.
- **Record:** `embed` carries `$type: app.bsky.embed.external` with required `external {uri,title,description}` and optional `thumb` blob.
- **Reading:** canonical post and compact quote responses expose `external {uri,title,description,thumb? {cid,mime,size,url}}`. Images-win shaping omits external when a federated record contains both.
- **Interaction:** tapping a card opens its validated final URL, including the selected source fragment, through the existing external launcher.

## 15. Data / Persistence Impact

- Public record: additive open-union reference to standard `app.bsky.embed.external`; no CraftSky-specific external schema.
- Public AppView storage: no new column. `craftsky_posts.record JSONB` remains authoritative, and shared reads project its standard external object.
- Private scheduled payload: add optional frozen external metadata and optional thumbnail media ID/metadata. Existing scheduled private-media rows/object storage hold the bytes.
- Local drafts: unchanged format; no preview data is persisted.
- Migration required: **No database migration expected.** Lexicon regeneration and scheduled payload codec changes are required.
- Backwards compatibility: existing records/schedules/drafts remain valid; absent external renders as today. This project is pre-production, but open-union compatibility is still preserved.

## 16. UI / API / CLI Impact

- UI: standard-composer loading/success carousel, left/right controls, position semantics, session dismiss plus Undo, image/quote suppression, unchanged image-required project composer, full external card, and compact quote external card.
- API: new `POST /v1/link-previews` with an optional thumbnail encoded as padded RFC 4648 base64 in JSON and a 1,000,000 decoded-byte cap; `POST /v1/posts` gains `embed.external`; post/quote responses gain `external`; scheduled payload requests/responses gain optional external state.
- CLI: none.
- Background jobs: no new job. Existing scheduled publication logic gains external-thumbnail upload/embed support.

## 17. Security / Privacy / Permissions

- Authentication: standard bearer session plus required device identity; production feature flag checked before egress.
- Authorization: same authenticated membership boundary as post composition; dedicated per-token and per-device limits.
- Outbound safety: public-routable-only DNS, mixed-answer rejection, pinned sockets, standard ports, redirect revalidation, no userinfo, bounded schemes/time/bytes/counts, and no unreviewed proxy.
- Request headers: no cookies, authorization, referer, or user content are forwarded. Use a stable CraftSky-identifying User-Agent.
- Sensitive data: URL/metadata is unpublished user intent until posting. It may transit the target and authenticated response but must not enter telemetry. Scheduled metadata/bytes remain owner-private until publication.
- Content handling: no scripts, active content, PDF, or full-page rendering; HTML tokenization and image decoding only.

## 18. Observability

- Client events: none; do not add product analytics or URL-bearing breadcrumbs.
- Logs: request ID plus bounded stage, result/error class, upstream status class, redirect-count/byte bucket, and duration only. No host or content.
- Metrics: bounded request outcome/error class and duration histogram; no URL/host/identity dimensions.
- Traces/Sentry: same bounded categories and privacy sentinel tests; no request/response bodies or dependency error strings containing target data.
- Alerts: none in v1.
