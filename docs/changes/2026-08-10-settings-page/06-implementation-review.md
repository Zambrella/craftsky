# Implementation Review: Settings Page And Account Management

## Verdict

Status: Changes required
Reviewer: Codex
Date: 2026-08-11
Risk level: High

## Summary

The non-destructive Settings, About, Account, Notifications, switching, cache, version, and Sign out work is substantially implemented and its focused Flutter coverage is green. The server implementation also establishes the intended owner/namespace/blob boundaries, durable operation model, restricted status access, deletion-only OAuth binding, private cleanup components, and indexer-owned convergence shape.

The destructive workflow is not ready to merge or hand off, however. Four recoverability/convergence counterexamples can permanently strand an operation: abandoned or expired pre-acceptance intents are not removed, tracked Tap receipt failures can still be poison-acknowledged, a delete observed before expected-record registration is discarded, and a successful PDS delete followed by marker persistence failure cannot repair its missing marker. Several approved Must-level tests are represented by narrower component tests than the acceptance specification requires, status rows do not refresh unless their page is opened, lifecycle telemetry is not wired into production paths, and deletion OAuth request metadata is added after rather than during auth-request persistence. These are behavioral, security, privacy, and traceability findings for another TDD pass, not UI-polish work.

## Risk Review

- Risk level: High.
- Risk notes: This feature permanently deletes federated records and private application data after ordinary access is revoked. The highest risks are operations that cannot be retried to convergence, Tap events that are acknowledged without durable receipts, incomplete private-data proof, and authorization metadata that is not persisted at the planned atomic boundary. These failures are not cosmetic: they can leave a user unable to retry or leave a non-terminal deletion job without a path to success.
- Approval notes: Not approved for merge, destructive real-stack validation, or release handoff. The owner/DID/namespace/blob boundary is appropriately narrow in the reviewed code, but the durable recovery and evidence gaps must be corrected first. Manual destructive validation must continue to use only a disposable development AT/PDS account after automated review is green.

## UI Polish Recommendation

- Recommendation: Optional
- Reason: The implemented Settings information architecture and action semantics appear coherent in automated coverage, while the unresolved issues are behavioral and must return to TDD. A small visual/accessibility pass can still be useful after those fixes and the manual responsive check.
- Suggested polish notes: Verify compact/large and RTL layouts, long localized deletion/status copy, keyboard/focus flow, disabled switcher-row semantics, destructive/error colours, and the centralized support-link presentation. Do not use polish to change polling, cancellation, authorization, persistence, or deletion behavior.
