# AV-002, AV-003, AV-006, and AV-007 — Account lifecycle and external-effect fencing

- Findings: AV-002, AV-003, AV-006, AV-007
- Severities: High (all four findings)
- Priority/order: Lifecycle and authorization foundation; land atomically with the grouped OAuth-handoff and session-integrity plans, before enabling account deletion or scheduled private media outside development
- Status: Planned
- Coordination note: AV-006/explicit-deletion and AV-007 implementation each require the explicit product-contract decisions described below
- Sources: [AV-002](../2026-08-12-appview-code-audit.md#av-002--terminal-did-deletion-leaves-a-ghost-account-and-privatepublic-data), [AV-003](../2026-08-12-appview-code-audit.md#av-003--departed-members-retain-usable-sessions-and-member-write-access), [AV-006](../2026-08-12-appview-code-audit.md#av-006--account-deletion-can-leave-an-untracked-private-media-object), [AV-007](../2026-08-12-appview-code-audit.md#av-007--automatic-follow-can-write-publicly-after-departure-or-deletion)

## Shared implementation strategy

Introduce one AppView-owned lifecycle for each DID and one owner-effect fence shared by membership transitions, terminal identity cleanup, explicit CraftSky deletion, private-object effects, and PDS effects. Lifecycle state, not the continued existence of a bearer or an already-claimed job, becomes the authority to act.

The owner lifecycle has these meaningful states:

1. `active`: the DID has current CraftSky membership and may use member routes and begin effects.
2. `departed`: the CraftSky profile record is absent. Existing credentials and queued effects are disabled, while retained private data follows the documented departure policy.
3. `deletion_pending`: the owner has started the fresh-reauthentication deletion flow. Normal member access and effects are suspended, but the narrowly scoped cancel and deletion-completion capabilities remain available.
4. `deleting`: exact-handle confirmation has been accepted. Only the deletion worker's typed, owner/job-bound capability may use the dedicated OAuth session to list and delete registered `social.craftsky.*` records.
5. `terminal`: AppView has received a terminal identity event. This state is irreversible, credentials are locally unusable, a committed terminal-visibility tombstone excludes every retained row from serving/effect paths, exhaustive physical purge is durably inventoried, and replay cannot resurrect the DID.

Every transition increments an owner generation. The same lifecycle row carries a positive monotonic auth epoch; departure, terminal state, and DID-wide logout increment it so every old auth request, parent, child, exchange, and receipt becomes unusable at one owner-scoped linearization point. Work created while an owner is active records its generation and must still match it when claimed and immediately before an effect. A session-level PostgreSQL advisory fence provides the cross-process linearization boundary:

- Ordinary outbound PDS/object effects acquire a shared owner fence, then re-read lifecycle, membership, job lease, generation, and policy before performing the call. The fence remains held through the outbound call and its local compare-and-set completion while the process lives; a durable attempt record preserves any outcome-uncertain request across a crash.
- Membership departure, deletion intent/acceptance/cancellation, explicit deletion, and terminal purge acquire the exclusive owner fence. Normally progressing effects drain before the transition commits, and effects waiting behind the transition fail their final active-state check. A vanished advisory lock after process failure is not treated as proof that a remote system canceled an accepted request.
- Scheduled media additionally takes an object-key fence, after the owner fence, across reservation, object-store `Put` or `Delete`, and the corresponding database state transition.
- The exact cross-plan advisory order is every owner-effect fence in canonical DID order; optional object/work fence; every AV-009 parent-session lock in canonical `(DID, sessionID)` order; then begin the short transaction. The exact database row-lock order inside it is owner lifecycle/auth-epoch row; authorization-request rows by primary key; account-deletion operation if relevant; OAuth parent rows by session ID; CraftSky child rows by primary key; handoff exchange/receipt rows by primary key; cleanup/outbox rows by primary key. A path locks only the subsets it needs, but never a later class before an earlier one. Advisory locks use dedicated acquired `pgx.Conn` values, bounded acquisition contexts, and guaranteed unlock/discard behavior.

This is intentionally a breaking redesign. Because there are no production users, replace the implicit `craftsky_profiles`/bearer contract and scattered lifecycle handlers directly. Do not retain a route-policy default that silently means “authenticated but membership optional,” and do not add compatibility bypasses around the effect fence.

## Problem to solve

Four current paths disagree about when an owner stops being allowed to exist or act:

- A terminal DID event runs several independent cleanup handlers but leaves membership, public projections, credentials, recipient-owned data, and other private rows behind.
- Deleting the CraftSky profile row removes membership without revoking sessions, while most normal routes require authentication but not current membership.
- Scheduled-media upload commits an `uploading` row, releases its transaction lock, performs object I/O, and marks the row ready later; account deletion can remove the row and finish cleanup between those steps.
- The automatic-follow worker checks membership before selecting a session, but can call `PutRecord` after membership loss or deletion has already invalidated local work.

Patching each call site independently would leave new time-of-check/time-of-use gaps. The shared lifecycle and fence make departure/deletion completion a well-defined boundary across HTTP, workers, PostgreSQL, the private object store, and the PDS.

## Desired outcome and invariants

- `terminal` is irreversible and wins over every replay, profile event, callback, worker lease, or cancellation request for the DID.
- First login never relies on a missing lifecycle row as implicit authorization. Under the resolved-DID fence, auth start inserts a first-login departed/onboarding row with generation/auth epoch 1 if absent, re-reads it, and cannot overwrite a concurrent terminal tombstone.
- AppView does not acknowledge a terminal identity event until one fenced, cardinality-independent commit records the irreversible tombstone, increments the auth epoch, denies credentials/new effects, installs exhaustive durable purge-component and object-cleanup work, and makes the tombstone authoritative for every serving, search, notification, moderation, projection, and effect query. ACK never depends on deleting an unbounded number of owner/actor/recipient/subject rows in one Tap deadline. Physical purge proceeds in durable bounded batches, while the terminal anti-join/guard makes retained rows unreachable from the commit boundary onward.
- Terminal cleanup does not require an `account_deletion_operations` row and is idempotent under duplicate Tap delivery and process restart.
- A departed, deletion-pending, deleting, or terminal owner cannot authenticate for ordinary member work or begin a member-owned private mutation or external effect. A remote request accepted before an AppView crash is outcome-uncertain; its durable deterministic record identity, content fingerprint/CID when available, and originating generation are reconciled without authorizing a repeat. While the owner is departed, any resulting public PDS source remains non-serving. If reconciliation proves the PDS accepted the write before the transition linearized, the existing same-DID rejoin policy may project that still-current public record after a legitimate new membership activation; no old-generation job, credential, or unaccepted call is revived. `terminal` never reactivates.
- The explicit authorization matrix has no implicit membership-optional default. Only login, onboarding/rejoin, logout, lifecycle status, deletion cancellation/completion, and other enumerated recovery routes may operate without `active` membership.
- A lifecycle transition that returns success prevents any new effect from beginning afterward and has waited for every normally progressing earlier effect. A pre-call durable attempt records effects that may have been accepted remotely before an AppView crash; object writes remain tracked by deletion tombstones until removed. Because a PDS may finish a non-compensable request after its client disappears, the approved AV-007 branch either removes asynchronous automatic-follow PDS writes for strict closure or explicitly accepts/reconciles that late-write residual.
- An outbound effect is authorized from state re-read while its shared fence is held; a stale middleware check, bearer, generation, job lease, or in-memory decision is insufficient.
- An object key is always represented by either a live media row or durable cleanup work. A failed/abandoned `Put` cannot create an undiscoverable private object.
- The explicit permanent-deletion worker remains the sole PDS deletion exception: it can delete only the authenticated owner's registered `social.craftsky.*` collections after fresh PDS OAuth reauthentication and exact-handle confirmation.
- Terminal DID cleanup never calls a PDS delete API, and no cleanup path deletes `app.bsky.graph.follow`, another namespace, a PDS account/DID, or blobs directly.
- Fence acquisition, PDS/object I/O, cleanup claims, and reconciliation are bounded, cancelable, idempotent, and observable without logging credentials, object contents, or sensitive private data.

## Scope

### In scope

- Owner lifecycle schema, transition service, generation checks, durable terminal tombstone, and reconciliation state.
- Profile-record deletion and recreation semantics, terminal Tap identity handling, and explicit account-deletion intent/accept/cancel/worker transitions.
- Revocation or quarantine of CraftSky bearers and parent OAuth sessions on departure or terminal deletion through the shared session service.
- A fail-closed route authorization matrix and transaction-level active-generation guards for owner-scoped private mutations.
- A cross-process owner-effect fence and durable attempt record for PDS/private-object effects, with focused scheduled-media cleanup and an explicit product decision to remove automatic-follow writes or accept their cross-system crash residual.
- Immediate terminal invisibility/effect denial plus complete, durable owner/recipient private-data and public-projection purge in bounded batches.
- Schema inventory tests, deterministic race tests, reconciliation tooling, metrics, and operational recovery.

### Out of scope

- Changing the AT Protocol, lexicons, or which data is public on a PDS.
- Giving PDS access or refresh tokens to Flutter.
- Deleting a DID/PDS account or deleting PDS records in response to an external terminal identity event.
- Expanding explicit deletion beyond the registered `social.craftsky.*` collections or creating a reusable generic PDS-delete interface.
- Retrospectively deleting an `app.bsky.graph.follow` written before the lifecycle transition's linearization point. The fence prevents late writes; uncertain historical outcomes are reconciled and surfaced, not repaired by widening deletion authority.
- Tap retry/quarantine and order-independent projection work, owned by AV-004/AV-005, except that terminal tombstones must survive their replays.
- General session refresh/logout mechanics, owned by the grouped AV-009/010/011/020/021/035 plan; this plan supplies its departure/deletion triggers.

## Design decisions

### Persist one owner lifecycle and generation

Add `owner_lifecycles`, keyed by typed DID at the Go boundary, with constrained state, positive `generation`, positive `auth_epoch`, transition timestamps/reason, and terminal-purge completion fields. The row is the durable lock target and authorization authority; `craftsky_profiles` remains the public membership projection but no longer carries the entire security meaning by itself. `EnsureOnboardingOwner` creates a missing row as departed with generation/auth epoch 1 while the resolved-DID fence is held, then re-reads it; missing-row-as-implicit-epoch is forbidden.

Profile creation may change `departed` back to `active` only through the membership activation service and increments generation so retained work cannot revive. `terminal` can never transition. Completion of explicit CraftSky deletion leaves the DID departed and data-free; a later rejoin must be a new authenticated/onboarding transition, not a stale job or historical replay.

Pending deletion is a real security state. `CreateIntent` must take the exclusive fence and move an active owner to `deletion_pending` before returning the authorization URL. Cancellation or intent expiry may restore `active` only if the owner still has a current profile and no accepted/terminal transition superseded the intent. Acceptance moves to `deleting`, revokes ordinary sessions, and preserves only the job-bound deletion credential.

### Use shared/exclusive session advisory locks as the effect fence

Use `pg_advisory_lock_shared` for ordinary effects and the matching exclusive advisory lock for lifecycle transitions. Derive the key in one package from the canonical DID; collisions may conservatively serialize unrelated owners but must never permit the same owner to use two keys. Hold the lock on one dedicated connection for the whole critical section, including network I/O, without holding an open database transaction across that I/O.

The helper API should make unsafe use difficult, for example `WithActiveEffect(ctx, owner, expectedGeneration, fn)` and `WithTransition(ctx, owner, fn)`. The callback passed to `WithActiveEffect` receives the revalidated generation and may open short transactions. A transition callback receives a transaction-capable lifecycle store. Do not expose raw lock/unlock helpers broadly.

### Enforce membership twice

Replace `CurrentMemberRequired bool` with an explicit, non-zero route access class such as `Anonymous`, `AuthenticatedRecovery`, and `CurrentMember`. Route construction/tests fail when a policy omits its class. All normal reads, private stores, uploads, and PDS mutations become `CurrentMember`; the recovery class is a short allowlist.

Middleware embeds the observed owner generation in context. Each owner-scoped private mutation rechecks `active` membership/generation in its transaction, and each external effect persists an attempt and rechecks under the owner fence before calling its remote system. This prevents a request that passed middleware before departure from beginning a private or public write afterward. A request already accepted remotely before an AppView crash remains an explicitly outcome-uncertain pre-transition attempt; lifecycle/source tombstones block local resurrection while reconciliation records the result without issuing another unauthorized write.

The ordinary PDS executor must allocate deterministic record identity before the call and persist the owner generation plus a canonical content fingerprint (and expected/result CID where computable) in the attempt row. Tap ingestion joins a matching URI/version to that disposition. Departure marks unresolved attempts `outcome_unknown_pre_transition`, forbids any repeat, and keeps observed source non-serving while membership is absent. Reconciliation then distinguishes proved-not-accepted (no record may be created), accepted/current public PDS state (eligible under the established same-DID rejoin projection policy), and mismatch requiring operator/PDS reconciliation. This rule applies only to known AppView-originated attempts; it never treats a PDS record as absent merely because local completion was lost. Terminal tombstones and explicit-deletion rules remain permanent overrides.

### Keep terminal purge and explicit PDS deletion separate

Factor the database cleanup inventory into transaction-capable owner purge components that do not assume an account-deletion operation. The terminal identity service commits a minimal `terminal` tombstone, auth/effect denial, one fixed-size ledger entry for every declared purge component/role, and all known external-cleanup intents before ACK. Every serving/effect SQL path must consult the authoritative terminal set: direct-owner rows anti-join the terminal lifecycle by owner/actor/source DID, recipient surfaces additionally suppress terminal actor/subject/source references, feeds/search/relationship/moderation queries suppress every role whose terminal state would expose or apply that account, and projectors refuse to materialize visible/effective state for a terminal DID. A bounded purge worker then deletes each inventoried component in keyset batches and marks its ledger entry complete. A schema-backed inventory/query-contract test fails when a new DID-bearing table or sqlc serving/effect query lacks a declared role, terminal predicate, and purge action. This is a systematic database/query invariant, not an optional handler-side filter.

Explicit deletion reuses private cleanup but retains its accepted operation and fresh reauthentication checks. Its OAuth parent uses a purpose-specific state such as `deletion_only`, which ordinary session lookup/PDS factories reject. Only a typed `ResumeDeletionSession(jobID, owner, sessionID, credentialGeneration)` path may load it under the owner/parent locks after verifying the accepted deleting operation and current worker lease. This resolves the pending-handoff lifecycle without making the deletion credential an ordinary login. Cancel/expiry of an unaccepted intent transitions the bound parent to cleanup; completion or terminal failure cleans the accepted parent. If accepted-job refresh is terminal, the job becomes `reauth_required`; a later ordinary fresh-sign-in resolves the same deleting DID, is server-derived into a job-bound deletion replacement, mints no bearer/membership, and atomically replaces the credential generation. No status/recovery credential or generic PDS resume route is added.

The explicit PDS deleter retains exactly `ListRecords` and `DeleteRecord`, and the collection allowlist remains `CraftskyRecordCollections()`. Neither the terminal purge nor the general owner-effect service receives that capability.

Accepted explicit deletion also owns the outcome-uncertain attempts for ordinary writes in those registered collections. Before reporting completion, the job must fence new writes, enumerate all durable pre-transition attempts, and reach one of two safe outcomes for each deterministic AT URI: prove the request failed before remote acceptance, or repeatedly list/read and delete that exact owner record under the existing job-bound authority. A crash may let an accepted write commit after an initially empty list/delete pass, so the job retains per-key deletion tombstones and repeats the scan/read/delete until a tested PDS settlement bound plus final scan has elapsed. If the PDS offers no finite settlement guarantee, the small job/tombstones remain active and reconciled rather than declaring the account data-free. This authority remains limited to the authenticated owner's registered `social.craftsky.*` collections; it cannot delete follows, blobs, the DID, or another namespace.

This safety rule conflicts with the approved lean deletion contract in `docs/changes/2026-08-10-settings-page/01-requirements.md`, which requires terminal success to remove the operation/OAuth authority and retain no deletion checkpoint, artifact, or audit state. Before implementation, explicitly revise that requirements/acceptance/review/plan set to choose one honest branch: (a) permit minimal non-secret, exact-key safety tombstones as a narrow temporary exception until uncertainty converges, after which they are removed; or (b) require a verified PDS/object-store settlement bound or staged protocol that makes the final scan/delete authoritative and permits complete state removal. Without either, the job must not claim terminal data-free success. Breaking schema compatibility does not silently override the already approved data-minimization contract.

### Fence the complete scheduled-media object effect

For `PrivateMediaService.Put`, acquire the active owner fence and object fence before reservation, keep them through `PrivateObjectStore.Put`, and perform the ready compare-and-set before release. Account/profile/terminal cleanup acquires the exclusive owner fence before selecting media, deleting rows, and enqueueing cleanup. Ordinary delete uses the same owner/object order.

Use generation-specific object keys (or add an immutable upload generation to the existing key) so a retry cannot collide with a completed cleanup from an older lifecycle. Before calling the object store, persist an upload-attempt ID, start time, and hard remote-call deadline/settlement deadline in the `uploading` reservation. The remote `Put` context must end no later than that deadline. A process crash after `Put` begins but before ready-state commit leaves the reservation and attempt tombstone for lifecycle/expiry cleanup.

An advisory lock disappearing on process crash is not proof that the remote store cannot still finish an accepted request. Cleanup may issue an early idempotent delete/HEAD, but it retains an immutable deletion tombstone and periodically repeats delete/HEAD for that generation-specific key. A finite `settling`/completion point is allowed only when the configured object backend has a tested, documented maximum server-side settlement bound; in that case the quiescence deadline must exceed the maximum remote `Put` deadline plus that bound and margin, followed by a final delete/HEAD. Without such a backend guarantee, do not infer impossibility from elapsed client time: retain the small tombstone indefinitely and keep it in the bounded reconciliation sweep. An unknown or over-deadline outcome remains durable and retryable rather than declaring absence.

### Resolve the non-compensable automatic-follow contract

The AppView cannot prove that a PDS canceled an accepted `PutRecord` after the AppView process crashed, and project policy correctly forbids deleting `app.bsky.graph.follow` as cleanup. The current user-approved Instagram requirements explicitly require durable automatic following, while AV-007's strict closure requires that no public write can complete after departure. Those two contracts cannot both be guaranteed across PostgreSQL and an independently committing PDS.

Before implementation, obtain an explicit product/requirements decision and update `docs/changes/2026-07-11-instagram-dm-verification/01-requirements.md` plus its acceptance/design/implementation artifacts. The recommended strict-safety decision is to retire the automatic-follow PDS-write capability: Instagram matching may create a private, lifecycle-bound suggestion, and only an explicit current-member API action requests the ordinary follow write. The alternative is to retain deterministic/idempotent automatic `PutRecord` with a durable pre-call attempt, shared importer/target fences while alive, and read reconciliation after crash—but explicitly accept and test the residual that a request accepted before crash may commit after departure. Do not implement a hybrid that promises strict post-transition non-publication while retaining the unrecallable background write.

## How the shared update closes each finding

### AV-002 — Terminal DID deletion leaves a ghost account and private/public data

`terminalIdentityDeletion` becomes one fenced owner transition rather than a list of partial handlers. The exclusive fence first drains normally progressing effects; the transition then writes an irreversible tombstone, disables credentials/new work, commits the complete fixed component inventory and cleanup intents, and activates terminal predicates across all serving/effect queries before Tap may ACK. Actor-only notification cleanup is replaced by role-complete owner/recipient handling, and public profile, content, interaction, relationship, search, notification, identity-cache, moderation, and private components are deleted by restart-safe keyset workers. Duplicate delivery observes/resumes the same inventory and cannot resurrect or expose the account, even while physical rows remain.

### AV-003 — Departed members retain usable sessions and member-write access

The profile delete index path calls the lifecycle service while holding the exclusive effect fence. It marks the owner departed, increments generation, revokes/quarantines all ordinary sessions, and cancels owner work in the same transition before deleting membership. The explicit route-access class makes all normal API surfaces current-member-only, while mutation/effect rechecks prevent new calls after transition. A stale bearer therefore fails authentication or membership authorization and cannot reach a private store or PDS client. A remote call accepted before an AppView crash is retained as an ambiguous earlier attempt, never repeated under the departed generation, and hidden while membership is absent. If it reconciles as valid pre-transition public PDS state, the existing same-DID rejoin policy may surface it; no old credential, queued job, or never-accepted call is revived.

### AV-006 — Account deletion can leave an untracked private-media object

Upload owns both the owner and object fences from reservation through object creation and the ready CAS. Deletion cannot snapshot the media attempt until the upload has either committed ready state or failed/crashed. Once deletion acquires the exclusive fence, no new upload may pass the active-state recheck; it enqueues every known generation-specific object while retaining the upload-attempt/deletion tombstone. Cleanup cannot complete while a live upload holds the fence. After a crash it either uses a proven backend settlement bound plus final delete/HEAD, or retains and periodically reprocesses the tombstone indefinitely so a delayed remote creation is never untracked.

### AV-007 — Automatic-follow can write publicly after departure or deletion

AV-007 closes only after the approved branch is implemented honestly. Under the recommended strict branch, the automatic-follow worker no longer performs a PDS write; it may persist a private suggestion after checking both participants, but has no writer/session capability and lifecycle departure deletes or invalidates the suggestion. Under the residual-acceptance branch, it acquires shared importer/target fences in canonical order, persists a pre-call attempt, rechecks both lifecycles, uses deterministic `PutRecord`, and read-reconciles unknown outcomes; the product contract explicitly permits the accepted-before-crash late-write residual. Neither branch grants cleanup deletion authority over `app.bsky.graph.follow`.

## Data, schema, migration, and reconciliation plan

- Add `owner_lifecycles` with `owner_did` primary key, constrained state, positive monotonic generation and auth epoch, transition timestamps/reason, terminal timestamp, purge completion timestamp, and updated timestamp. Retain terminal rows as minimal tombstones; do not cascade-delete them with `craftsky_profiles`. Copy auth epoch to every authorization request, parent, child, exchange, and receipt, and index owner/epoch invalidation.
- Add `owner_generation` to scheduled posts/media and other durable owner-effect jobs. Dry-run is the default, and repair requires an explicit scoped flag.

## API, client, configuration, and operations impact

- The `/v1` authorization contract changes: normal authenticated routes now require `active` current membership. Stale departed bearers return the standard invalid-session response after revocation; an explicitly enumerated onboarding/deletion flow in a non-active lifecycle receives the stable camelCase error or completion response defined for that route. This does not create a deletion status/recovery credential.
- Add or formalize lifecycle status only for onboarding/rejoin; do not add deletion polling, post-acceptance status, or recovery state. Split create/rejoin from profile update rather than allowing a broad non-member `PUT /v1/profiles/me` path.
- Existing pre-acceptance account-deletion intent, cancel, reauthentication-complete, and acceptance routes must declare exactly which `deletion_pending` state they accept. Acceptance is terminal from the client's perspective and non-cancelable; `deleting` has no client status/recovery/cancel route. Normal APIs cannot accept the deletion-only OAuth parent or capability.
- Flutter must treat departure/session revocation as signed out and must not retry a rejected member mutation with the same bearer. Before acceptance, deletion reauthentication may use only the existing intent/cancel/reauth-complete/acceptance flow. After acceptance it removes the local account and receives no deletion status/recovery credential or polling route; later credential replacement, if needed, uses the ordinary fresh-sign-in entry as specified by the OAuth plan without restoring membership.
- The grouped OAuth-handoff implementation must provide verified App/Universal Link handling for both ordinary login completion and `account-deletion/reauth-complete`; removing the custom scheme before both paths migrate would break deletion.
- Add positive, bounded configuration for owner-fence acquisition/operation deadlines, object `Put` deadlines, optional object/PDS settlement bounds and margins, terminal pre-ACK transition budget, terminal purge keyset batch sizes, media/PDS reconciliation batch sizes, and cleanup retry/backoff. Validate at startup through AV-022/023/024/030 that the fixed pre-ACK tombstone/epoch/ledger commit plus margin fits the Tap handler deadline; never claim that configuration bounds an owner's row cardinality. Finite tombstone/deletion-job completion is enabled only for a tested backend/PDS server-side bound whose settlement point dominates the latest permitted remote write completion plus margin. Otherwise default to retained tombstones/reconciliation, not an invented timeout.
- Alert on non-active owners with active credentials, terminal purge age/failure, effect-fence acquisition timeouts, stale generation claims, uploading-media age, and cleanup backlog. On the strict AV-007 branch, alert on any attempted use of the retired writer; on the residual branch, report durable attempts by pending/ambiguous/reconciled outcome and oldest age, including delayed commits after departure. Logs use DID hashes or existing safe correlation IDs, never tokens, handles, media metadata/content, or raw private records.
- Provide dry-run lifecycle audit/reconciliation commands scoped to one DID or bounded batch. Terminal replay and idempotent repair may remove AppView data, but no operational command may invoke PDS deletion except the accepted job-bound deletion worker.

## Security, failure, and race considerations

- An advisory lock is connection-scoped. Acquire it on a dedicated `pgx.Conn`, never return that connection to the pool while locked, explicitly unlock in `defer`, and close/discard the connection if unlock cannot be confirmed. Context cancellation and server shutdown must release it.
- Use one documented lock-key derivation and the global advisory order: every required owner-effect fence in canonical DID order, optional object/work fence, every parent-session lock in canonical `(DID, sessionID)` order, then a short transaction. Within it, lock owner lifecycle/auth epoch; authorization requests by primary key; account-deletion operation if relevant; OAuth parents by session ID; CraftSky children by primary key; exchange/receipt rows by primary key; cleanup/outbox rows by primary key. A path uses only required subsets and never reverses classes. A hash collision may reduce concurrency but cannot reduce safety. Never acquire an owner pair in caller-provided order, acquire in reverse, enter an owner fence from the AV-009 refresh coordinator, or wait for an exclusive transition while recursively holding a shared effect lock.
- Lifecycle state is re-read after lock acquisition. An HTTP middleware result, cached membership Boolean, selected background session, or claimed lease from before acquisition cannot authorize the effect.
- Avoid holding a SQL transaction during PDS/object network calls. The session advisory fence spans the call; short transactions before/after it enforce generation and lease compare-and-set updates.
- A transition request waits for normally progressing already-linearized effects but blocks later effects. If an AppView process crashed after a remote system accepted a request, the durable attempt remains outcome-uncertain and the transition may complete without claiming that the remote call was canceled. Fence acquisition has a bounded deadline; timeout leaves lifecycle unchanged and returns/retries as a dependency failure rather than partially deleting state.
- Process crash during a transition rolls back database changes and releases the fence. Process crash after terminal commit is safe because the tombstone denies owner access and every serving/effect query suppresses retained terminal references; durable component/object cleanup resumes from its keyset ledger.
- Process crash after object `Put` starts leaves its generation-specific `uploading` reservation and persisted attempt/deletion tombstone. An early absent HEAD/delete cannot erase tracking. A final post-quiescence delete/HEAD catches delayed creation only where a backend settlement bound is proven; otherwise recurring tombstone reconciliation catches and removes a remote request that completes at any later time.
- PDS timeouts are outcome-uncertain. Retain deterministic operation identifiers and reconcile by read where authorized; never repeat a non-idempotent write blindly. After lifecycle becomes non-active, do not perform a new write or broaden cleanup authority.
- A delayed PDS record is not retried merely because it was initially membership-blocked. Ingestion carries the originating effect generation and remote-boundary disposition through blocked work. While departed it remains hidden; on legitimate same-DID rejoin, only authoritative still-current PDS state proved/treated as accepted before transition follows the existing rejoin projection policy. Proved-not-accepted calls, old jobs, and CID/content mismatches are never guessed into eligibility, and terminal state always suppresses them.
- Explicit owner-authorized CraftSky deletion is the narrow exception that may reconcile and re-delete a late ambiguous `social.craftsky.*` write. An empty first scan or vanished AppView lock is not completion; retain exact-key tombstones and the accepted operation until the PDS settlement contract plus final scan permits completion, or indefinitely when no finite guarantee exists.
- Target lifecycle matters on either AV-007 branch. Strict-branch suggestion creation/retrieval rechecks both participant generations and never crosses a PDS effect boundary. Residual-branch automatic write acquires importer/target fences canonically, persists its attempt before the call, rechecks both, and never repeats an ambiguous attempt after either transition; a delayed accepted commit remains the explicitly approved residual.
- Terminal purge must distinguish references owned by the deleted DID from unrelated users' public records that merely reference it. The schema inventory gives each role an explicit action and tests isolation.
- The deletion-only OAuth state and job-bound resume method are mandatory capability boundaries. They must not be accepted by ordinary `GetSession`, background selection, bearer issuance, or owner-effect execution.

## Per-ID traceability and acceptance criteria

### AV-002

- [ ] Before a terminal identity event is acknowledged, one fenced, cardinality-independent commit records the irreversible tombstone, auth/effect denial, all known object-cleanup intents, and an exhaustive fixed component/role ledger; it never requires an unbounded per-owner delete.
- [ ] Migration/query inventory coverage proves every public, private, other-account-visible, or behaviorally effective DID role is terminal-gated immediately and assigned a bounded physical purge action.
- [ ] Duplicate delivery and injected partial failure converge without a ghost profile, relationship, session, push subscription, scheduled item, or private row.
- [ ] Terminal commit increments auth epoch and invalidates every parent, child, authorization request, exchange, and receipt; a callback/save/finalizer racing the event cannot recreate one afterward.
- [ ] Terminal cleanup never requires an account-deletion operation and never calls a PDS delete API.
- [ ] Historical profile/Tap replay cannot reactivate a terminal DID.
- [ ] With all purge workers paused after ACK and terminal-owned/referencing rows still physically present, every profile/feed/post/search/relationship/moderation/notification read and effect path suppresses the terminal DID; batched workers later remove all inventoried rows.

### AV-003

- [ ] Profile deletion performs one fenced departure transition that increments generation and auth epoch, invalidates work, and revokes/quarantines every active or pending ordinary auth artifact.
- [ ] Every normal `/v1` route is explicitly current-member-only; the non-member/recovery allowlist is documented and mechanically tested.
- [ ] Private mutations and PDS/object effects recheck active lifecycle/generation at their commit/effect boundary rather than relying only on middleware.
- [ ] A stale bearer or request that has not crossed the final fenced effect boundary before departure cannot begin a PDS/private write afterward; an accepted-before-crash remote attempt is durably marked ambiguous and never repeated, stays hidden while departed, and may reproject only as authoritative accepted pre-transition public PDS state under the approved same-DID rejoin rule.
- [ ] Rejoin creates a new generation and cannot revive retained jobs or sessions from the departed generation.

### AV-006

- [ ] Upload, ready CAS, ordinary deletion, account/terminal purge, and cleanup share the owner/object fence and one acquisition order.
- [ ] The deterministic paused-upload/deletion test leaves neither an untracked object nor a missing cleanup job.
- [ ] Crash recovery handles object creation before ready-state commit and a remote `Put` that completes after the client process/lock disappears, using the retained generation-specific attempt/deletion tombstone and repeated delete/HEAD; finite completion requires a tested backend settlement bound.
- [ ] Reconciliation is bounded, dry-run capable, idempotent, and tested against absent and present objects.

### Explicit deletion shared gate

- [ ] The lean deletion requirements, acceptance tests, review, and implementation plan explicitly approve either temporary minimal safety tombstones until convergence or a verified settlement/staged protocol that permits artifact-free finalization; implementation does not silently retain checkpoints or silently accept late records.
- [ ] An accepted deletion job inventories every ambiguous pre-transition write in registered `social.craftsky.*` collections, retains exact-URI deletion tombstones, and cannot report data-free after only an empty initial scan.
- [ ] The accepted-write → AppView crash → empty deletion scan → delayed PDS commit barrier converges by re-scan/re-delete before completion; without a tested finite PDS settlement bound, the narrow job remains reconciling rather than fabricating completion.
- [ ] This reconciliation authority is exact-owner, exact-job, and exact registered collection; it cannot delete `app.bsky.graph.follow`, blobs, another namespace, or the DID/PDS account.
- [ ] Terminal success satisfies the revised minimization branch: all temporary tombstones/job/OAuth state are removed after proven convergence, and no deletion audit/status/receipt or unrelated private data remains.
