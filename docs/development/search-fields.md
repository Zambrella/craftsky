# Searchable-field contract

Contract revision **4**. Application taxonomy **catalog-v1.json**, version **5**.

`appview/internal/api/search_fields.go` is the executable keyword allowlist;
`appview/internal/projectcatalog/catalog-v1.json` supplies stable values, labels,
aliases, and directional parent relationships. Flutter and Svelte options are generated by
`python3 scripts/project-catalog`; `--check` runs in `appview-check`. Catalog
changes increment its version; keyword/weight changes increment the search
revision in relevance cursors. Old cursors fail with `invalid_cursor` rather than
mixing rankings. Records retain their original values and require no rewrite.

## Keyword fields

- Weight 1.0: post text, project title, pattern name.
- Weight 0.7: pattern designer and publisher.
- Weight 0.4: material text; primary and additional crafts; project status;
  pattern difficulty and self-drafted declaration; colors; project type and
  subtype; yarn weight; fit notes; piecing technique and quilting method;
  project techniques and their subtypes; embroidery methods and styles;
  knitting, crochet and felting methods; spinning drafting and plying techniques;
  dye application method; macramé knots; weaving loom type and structure;
  felting form. Previously authored values continue to participate even when
  their fields have retired from the first-party composer.
- Weight 0.3: duration; needle and hook sizes; made/finished sizes; gauge stitch,
  row, measurement, and unit values. Decimal measurements retain their decimal
  separator during query tokenization.
- Weight 0.2: post/project tags and design tags.
- Weight 0.1 per image: image alt text, in its own field.

The listed detail fields participate under their applicable project craft. General post searches only
use general post fields; project metadata does not spill into general posts.
Unknown extension properties are preserved but never automatically searched.
Top-level post `crafts` is reserved metadata: it is preserved but does not
participate in keyword search, craft filtering, or tag discovery. Crafts inside
`project.common` supply keyword search and tag discovery; only the primary craft
supplies craft filtering.
Facet metadata, mention DIDs, raw pattern URLs, embed contents, timestamps,
duration-derived numeric estimates, import provenance, sponsored flags, and
technical identifiers do not participate in keyword matching. Visible facet text
participates through its owning field; actual tag facets retain tag discovery.
Machine model and needle spacing, spinning tool and yarn preparation or yield,
dye material, dye type, colour effect and recipe notes, Punch Needle foundation,
tool and loop height, cord and warp/weft inputs, sett, and felting gauges, core
and armature are outside keyword matching. Historical shared Materials text
continues to participate.

A present tool-size or pattern list supplies the effective values, including
when empty. When the list is absent, the legacy field supplies a singleton.
Each pattern contributes its own name, designer, publisher, difficulty and
self-drafted field with the weights above.

Vocabulary fields use English catalog labels, aliases, and ancestor labels.
Thus a cardigan is also searchable as a sweater, while an unspecified sweater
does not acquire a cardigan label. Equivalence groups are explicit; no fuzzy
merging of pattern identities or rewriting of authored metadata takes place.
Custom item names are keyword searchable. Their authors' selected project type
sets the browse category.
Language-aware matching, bounded typo fallback, result tiers, weights, stable
tie breaks, and query-bound cursors retain the established search semantics.

## Filtering and visibility

Project browse on `GET /v1/projects` and `GET /v1/public/projects` accepts
repeated query parameters for dropdown values. A project must match at least
one selected value in each active filter. Craft filters match the primary
craft, and craft-specific filters read the detail object for that craft. Both
first-party clients use the current catalogue choices for the selected craft
and release phase. All crafts offer status, pattern difficulty and the
self-drafted flag.

| Craft | Current craft-specific browse parameters |
|---|---|
| Knitting | `projectItem`, `knittingMethod` |
| Crochet | `projectItem`, `crochetMethod` |
| Sewing and Quilting | `projectItem` |
| Embroidery | `projectItem`, `embroideryMethod`, `embroideryStyle` |
| Spinning | Shared filters only |
| Dyeing, Punch Needle and Macramé | `projectItem` |
| Weaving | `projectItem`, `loomType` |
| Felting | `projectItem`, `feltingMethod` |

Each `projectItem` value accepts a catalog ID for a type or subtype. Repeated
values match any selected item, up to 10 entries. Parent matches include
descendants. A Bag filter can include Tote bag and Backpack. A Tote bag filter
matches that subtype and its equivalents. Custom text appears in keyword
results, and the selected type still matches its type filter. Legacy Dyeing
material forms and known historical item identifiers contribute to the
corresponding current filters.

Earlier URLs can still use `projectType` and `projectSubtype`. When both are
present, a project must match both. When `projectItem` is also present, a
project must also match one of its values.

Embroidery Method and Style filter independently on current records. When
both values come from old grouped entries, the same saved group must satisfy
both filters. Crochet falls back to an explicit old Tunisian technique and
Felting falls back to its old single method when its current list is absent.
An explicit empty list takes precedence.

AppView still accepts the retired browse parameters from earlier clients.
Legacy grouped Knitting technique and subtype filters must match the same
entry. Legacy needle and hook size filters use the effective list, including the
scalar fallback when absent. Pattern difficulty and self-drafted must match the
same entry when combined. Keyword requests remain text-only.
The primary/additional crafts are also used for grouped tag discovery. Public
records contain no private project-management state.

Eligibility is applied before matching and typo candidates. Existing media,
moderation, owner lifecycle, block/mute, and content-language restrictions on
each search surface remain in force. No business/subscription boost is added.
Timeline ordering remains chronological and independent of search relevance.

## Hashtags

Newly indexed or updated posts contribute at most **10 distinct hashtags** to
hashtag search, discovery and suggestions. The same budget covers the whole
post/project: post text facets, structured project tags, and the name, designer
and publisher facets for each effective pattern in saved order. Material facets
follow in list order. Tags are trimmed and
lowercased before deduplication; the first ten identities win. Repeated tags
consume one slot. Both clients use the same priority when painting and publishing
composer hashtags; excess hashtags remain ordinary text, and removing an earlier
tag makes room for the next one. Links and mentions retain their own facets.

AppView accepts over-budget records from other clients and caps only its tag
projections and immediate publication response. Source PDS records are preserved.
There is no historical backfill or read-time cap; existing indexed rows are
unchanged until a subsequent indexing update. Ordinary keyword matching still
includes visible text.

Search, grouped discovery, and composer suggestions include all historical
eligible posts. `postCount` is the all-time distinct-post count for that tag,
not occurrences and not a recent-activity count. Case variants share one count;
the display spelling is selected from the same eligible population. Existing
surface-specific eligibility is retained, including the composer's existing
absence of viewer relationship exclusions. Deleted, hidden, or otherwise
ineligible posts do not vote on surfaces that exclude them.

## Change checklist

When adding a project property, update the keyword allowlist or explicitly list
its exclusion here, plus coverage fixtures. Add aliases/parents to the catalog,
validate acyclic relationships and token coverage, regenerate client data,
and test record updates/deletes, unknown-field preservation, visibility,
language matching, pagination, and historical tag counts. Lexicon changes also
require ADR, `just lexgen`, `just lexgen-check`, and reviewed publication last.
