# Searchable-field contract

Contract revision: **2**. Application taxonomy: **catalog-v1.json**, version **1**.

`appview/internal/api/search_fields.go` is the executable keyword allowlist;
`appview/internal/projectcatalog/catalog-v1.json` supplies stable values, labels,
aliases, and directional parent relationships. Flutter options are generated by
`python3 scripts/project-catalog`; `--check` runs in `appview-check`. Catalog
changes increment its version; keyword/weight changes increment the search
revision in relevance cursors. Old cursors fail with `invalid_cursor` rather than
mixing rankings. Records retain their original values and require no rewrite.

## Keyword fields

- Weight 1.0: post text, project title, pattern name.
- Weight 0.7: pattern designer and publisher.
- Weight 0.4: material text; primary and additional crafts; project status;
  pattern difficulty and self-drafted declaration; colors; project type and
  subtype; yarn weight; fit notes; piecing technique and quilting method.
- Weight 0.3: duration; needle and hook sizes; made/finished sizes; gauge stitch,
  row, measurement, and unit values. Decimal measurements retain their decimal
  separator during query tokenization.
- Weight 0.2: post/project tags and design tags.
- Weight 0.1 per image: image alt text, in its own field.

Every applicable craft's detail fields participate. General post searches only
use general post fields; project metadata does not spill into general posts.
Unknown extension properties are preserved but never automatically searched.
Top-level post `crafts` is reserved metadata: it is preserved but does not
participate in keyword search, craft filtering, or tag discovery. Crafts inside
`project.common` supply keyword search and tag discovery; only the primary craft
supplies craft filtering.
Facet metadata, mention DIDs, raw pattern URLs, embed contents, timestamps,
duration-derived numeric estimates, import provenance, sponsored flags, and
technical identifiers do not participate in keyword matching. Visible facet text
participates through its owning field; actual tag facets retain tag discovery.

Vocabulary fields use English catalog labels, aliases, and ancestor labels.
Thus a cardigan is also searchable as a sweater, while an unspecified sweater
does not acquire a cardigan label. Equivalence groups are explicit; no fuzzy
merging of pattern identities or rewriting of authored metadata takes place.
Language-aware matching, bounded typo fallback, result tiers, weights, stable
tie breaks, and query-bound cursors retain the established search semantics.

## Filtering and visibility

Project browse filters continue to use their existing endpoint and canonical
values. Craft filters match only the primary craft, so a project appears only in
its primary craft's feed. The primary craft also owns the detail object.
Keyword requests remain text-only.
The primary/additional crafts are also used for grouped tag discovery. Public
records contain no private project-management state.

Eligibility is applied before matching and typo candidates. Existing media,
moderation, owner lifecycle, block/mute, and content-language restrictions on
each search surface remain in force. No business/subscription boost is added.
Timeline ordering remains chronological and independent of search relevance.

## Hashtags

Search, grouped discovery, and composer suggestions include all historical
eligible posts. `postCount` is the all-time distinct-post count for that tag,
not occurrences and not a recent-activity count. Case variants share one count;
the display spelling is selected from the same eligible population. Existing
surface-specific eligibility is retained, including the composer's existing
absence of viewer relationship exclusions. Deleted, hidden, or otherwise
ineligible posts do not vote on surfaces that exclude them.

## Change checklist

When adding a project property, update the keyword allowlist or explicitly list
its exclusion here, plus coverage fixtures. Add aliases/parents to the catalog,
validate acyclic relationships and token coverage, regenerate Flutter data,
and test record updates/deletes, unknown-field preservation, visibility,
language matching, pagination, and historical tag counts. Lexicon changes also
require ADR, `just lexgen`, `just lexgen-check`, and reviewed publication last.
